# ASM Tracing Technique (ARM64 Dart AOT)

The single highest-leverage skill in this kind of analysis: reading Blutter's addressed pseudocode precisely enough to answer questions an English paraphrase can't be trusted to answer correctly — argument order, which branch is actually taken, which field a value comes from.

## Why this matters more than it might seem

Reconstructed/paraphrased pseudocode (whether generated by you or by a user's IDE agent) is genuinely useful for getting oriented quickly, but it silently drops or rearranges detail that a real finding's severity often hinges on. In one real engagement, a paraphrase reported a function call as `decryptValue(lookupKey, storedValue)` — two arguments, in an order that wouldn't actually decrypt anything if taken literally. Manually re-tracing the raw registers showed the real call was `decryptValue(storedValue)` — one argument — with the second, load-bearing value (a device-bound password) pulled from an object field a few instructions later, inside a *different* function. Trusting the paraphrase would have produced a materially wrong finding about which key protects stored credentials.

**Rule of thumb: any finding whose severity depends on "does X actually happen, and with which exact inputs" needs the raw ASM, traced by hand, before it goes in a report.**

## Object layout & field access

- Dart AOT uses compressed (32-bit) pointers on 64-bit targets. Object fields sit at offsets following the pattern `0x7, 0xb, 0xf, 0x13, 0x17, 0x1b, 0x1f, 0x23, 0x27, 0x2b, 0x2f, ...` — each field N (0-indexed) sits at byte offset `4N + 7`. So `field_2f` is the object's 11th field (index 10).
- A field read looks like:
  ```
  LoadField: r2 = r0->field_7
      ldur w2, [x0, #7]
  DecompressPointer r2
      add x2, x2, HEAP, lsl #32
  ```
- A field write (`StoreField: r1->field_7 = r0`) is the same shape in reverse.
- Blutter sometimes prints a resolved name for a static field (`Field <ClassName.fieldName>: static ...`). When it doesn't (common for internal/private fields), don't guess a name — track it by its numeric field ID/offset consistently, and if it's load-bearing, ask for the constructor or initializer that assigns it, which usually resolves the ambiguity without needing Blutter to have named it.

## Calling conventions

- **Instance method calls:** `r1` = receiver (`this`), then `r2`, `r3`, `r5`... hold positional arguments in order (note: `r4` is commonly skipped/reserved for an argument descriptor in some call shapes — don't assume args are strictly contiguous by register number without checking).
- **Static/top-level calls:** no receiver; arguments typically start at `r1`.
- **`SetupParameters` comments at function entry** show the incoming-register → local-register/stack mapping, e.g. `SetupParameters(dynamic _ /* r2 => r3, fp-0x8 */, ...)`. Read this literally and track where each value actually ends up — don't assume the order matches whatever English parameter names a paraphrase attached to them. Parameter *names* in a paraphrase are often the least reliable part of it; the register/stack mapping is the ground truth.
- To resolve a call site definitively: note which registers the **caller** sets immediately before the `bl` (branch-and-link), then check the **callee's own `SetupParameters`/entry code** to see how many of those registers it actually reads and what it does with each one. If the caller sets more registers than the callee's entry touches, the extra ones are unused for that particular call path — a common source of paraphrase errors that report an argument that's actually never read.

## Common instruction patterns worth recognizing

- **`tbnz`/`tbz` (test-bit-and-branch)** — single-bit boolean tests, common for feature flags and initialization-state checks. `tbnz` branches **when the bit is set**; the fallthrough path is what runs when it's clear. Get this backwards and you'll invert a finding's conclusion.
- **Smi (small integer) boxing** — `BoxInt64Instr` sequences like `sbfiz x0, x2, #1, #0x1f` encode a raw integer as `(value << 1)`. A boxed comparison like `cmp w0, #6` is testing the raw value against `6 >> 1 = 3`, not `6` — check the shift amount before trusting a literal comparison value.
- **`StoreStaticField(0xNNNN, ...)` / `LoadStaticField(0xNNNN)`** via `THR::field_table_values` — global/static field access, addressed by a numeric field ID. Track these IDs across the whole artifact; the same ID read in one function and written in another is how you connect, e.g., an entrypoint's environment-string assignment to a later function that consumes it.
- **DI/service-locator registration (Stacked-style `registerLazySingleton<Interface>(factory, registerFor: {envSet})`)** — resolve two things independently: (1) the literal environment-string set (e.g. `{"prod","test"}` vs `{"dev"}`) attached to each registration, and (2) which concrete class each registration's closure actually allocates (trace the closure's address to its `Allocate<ClassName>Stub` call). Don't assume symmetry between registrations for different interfaces — verify each one, though in practice a consistent pattern across several interfaces is decent evidence (not proof) the same pattern holds for others you haven't individually checked.

## Worked pattern: resolving a caller/callee argument mismatch

1. Get the raw ASM for the **call site** (not just the callee). Note exactly which registers are set in the instructions immediately before the `bl`.
2. Get the raw ASM for the **callee's entry** (`SetupParameters` line + first several instructions). Note which of those registers it actually reads, and what it does with each.
3. If a paraphrase's argument count or order doesn't match what you traced, trust the trace. Write out the corrected call signature explicitly (e.g. "`decryptCipherText(encrypted=x1, decryptionKey=x2)`, not `(lookupKey, storedValue)` as reported") so the correction is auditable, not just asserted.
4. If the trace still leaves genuine ambiguity (e.g. an unnamed field whose origin you haven't seen), say so explicitly and name the exact next artifact (which constructor, which function) that would resolve it — don't paper over the gap with a confident-sounding guess.
